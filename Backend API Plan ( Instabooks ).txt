Backend Data Schema ( Instabooks )

user
- name
- email
- addresses: [string]
- photo
- cart []
    - book id
    - order quantity
- id


books
- title
- description
- pages
- author
- price
- cover photo
- quantity
- genre
- id


orders
- user_id
- products
    - book id
    - order quantity
- id
- status ( shipped | pending | cancelled )
- price at purchase
- created at
- shipping address
- payment status

Backend API Plan ( Instabooks )


Auth 

GET /auth/google  ( redirect to google auth page )

Request body: none
Request Header: none
Response: none ( redirects to google auth page )
Response Header: none


GET /auth/google/callback  ( callback endpoint for google auth )

Request body: none
Request Header: none
Response Header: none
Response: 
- 200: Redirect to frontend with auth id in query parameters (e.g. 
    /auth/google/verify/:auth_id)

Logger 

POST /logger  ( log events and errors )

Request body ( required fields since logs can contain variable data ):
- JSON: {
    "level": < log level e.g. "info" | "error" | "warn" >,
    "timestamp": < timestamp e.g. "2026-07-14T21:19:01.728Z" >,
    "event": < event description e.g. "User logged in" >,
    ...( optional fields for additional context, e.g. user_id, request_id, order_id, etc. )
}
Request Header: none
Response Header: none
Response:
- 202: ( No data returned, log accepted for processing )
- 400: {
    "status":"error",
    error: {
        "message": < error message >,
        "code": < error code >
    }
}



Footnote:
- logging and observability design should include user_id on 
  protected endpoints for better traceability, request_id on all endpoints for better correlation, 
  , error logging with stack traces for easier debugging, order_id on order related endpoints 
  for better traceability of order processing and summarized logs to prevent log flooding 
  while still capturing important events and errors.
